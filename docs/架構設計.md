# 架構設計

## 分層

```
cli.py ─► core/pipeline.py
            │ 1. find_extractor(url)          extractor/
            │ 2. extractor.extract() → MediaJob（純資料，只存 session_id）
            │ 3. 每條串流 protocol_for(kind)(ctx).run()   protocol/
            │ 4. ffmpeg 合併                   postprocess/
            ▼
   ┌──────────── session/ ────────────┐
   │ Session：CookieJar（唯一來源）    │◄── 提取器建立、設定 refresher
   │          headers / proxy          │
   │          refresh() single-flight  │
   └──────────────────────────────────┘
            ▲ 所有請求都透過 Session
   protocol/（HLS / DASH / FILE）── Segment ──► fetcher/（httpx / aria2 / curl / browser）
            │
            └─ backfill/（回溯策略）
```

| 目錄 | 職責 | 不負責 |
|---|---|---|
| `extractor/` | 解析網站、登入、建立 Session、產生 MediaJob、提供 refresh | 下載 |
| `session/` | cookies / headers / proxy 的唯一來源；刷新；瀏覽器同步 | 網站邏輯 |
| `protocol/` | 理解串流格式：播放清單、片段、金鑰、直播輪詢、回溯、本地清單 | 傳輸細節 |
| `fetcher/` | 把一個網址抓成一個檔案；並行限制（全域 / 每主機） | 格式 |
| `backfill/` | 由已知片段推出網址模板，探測更早的片段 | 下載 |
| `core/store.py` | 片段狀態，`backup/{title}/store.json`，斷點續傳 | |

## Session 規則（解決舊版 cookies 反覆抽出注入的問題）

1. **CookieJar 只有一份**。httpx client 直接共用該 jar（不是複製），伺服器的 Set-Cookie 立即生效。
2. 外部工具（aria2、curl、瀏覽器 fetch）需要時才以 `session.headers_for(url)` 產生標頭，依 RFC 規則挑選該網址適用的 cookie，不保存副本。
3. cookie 一律保留 domain / path / secure / expires；舊版只複製 name=value 會送錯網域。
4. `authority`：瀏覽器為權威時只會「瀏覽器 → jar」，`push_to_browser()` 會直接拒絕，避免互相覆蓋。
5. UA 以瀏覽器 `navigator.userAgent` 為準（`attach_browser`），爬蟲與下載的指紋一致。
6. 401/403 → `fetch_with_retry` 呼叫 `session.refresh(seen_version)`；同時失敗的請求只會觸發一次刷新。
7. 多視角需要獨立身分時用 `SessionManager.fork(id)`。
8. proxy 是 Session 欄位，所有 Fetcher 自動套用。

## 新增網站提取器

在 `streamdl/extractor/adapters/` 新增模組（可為資料夾），定義 `InfoExtractor` 子類別即可自動載入：

```python
class FooExtractor(InfoExtractor):
    config = ExtractorConfig(name="foo", valid_url_regex=r"foo\.com/live/", priority=10, backfill=False)

    async def extract(self, url, ctx):
        session = ctx.new_session({"Referer": "https://foo.com/"})
        # 需要瀏覽器時：browser = await ctx.new_browser(); await session.attach_browser(browser)
        session.set_refresher(self.refresh)
        ...
        return MediaJob(title=..., streams=[StreamSpec(kind=StreamKind.HLS, url=m3u8, title=..., session_id=session.id)])

    async def refresh(self, session):
        ...  # 重新登入 / 重新取得簽章
```

## 回溯

- `UrlDiffBackfill.build`：比較兩個片段網址，只允許「同一組數字」在一處或多處不同 → `{num}` 模板、補零位數、間距。若有第二組獨立變化（如每段簽章）則放棄。
- 間距 1：分段二分搜尋下界（舊版逐段切片 → 現在約 log2(距離) 次請求）。
- 間距 > 1（時間戳命名）：先試常見間距（舊版 Deltas），失敗再以 1.5 倍間距範圍並行掃描，並學習新間距。
- 啟用回溯時片段的排序鍵為網址中的數字，回溯片段與播放清單片段可直接合併排序。
- 加密且播放清單未給 IV 時，依 RFC 8216 以媒體序號為 IV；本地 `media.m3u8` 每段寫出明確 IV（舊版用全 0，在 MEDIA-SEQUENCE ≠ 0 時會錯）。
- 網站可用 `ExtractorConfig.backfill=False` 關閉（取代舊版 `SKIP_FORMAT_URLS`）。
- DASH：`SegmentTemplate` 本身就是模板（`parser.to_url_template`），不需比對網址；`$Number$` 走二分搜尋，`$Time$` 以 SegmentTimeline 的片段長度作為 `hints` 往前猜，最後再探測時間起點（串流開頭的片段長度常與其他片段不同）。
- `max_scan`：猜測失敗時的範圍掃描上限。HLS 時間戳命名需要掃描（預設不限）；DASH `$Time$` 的 timescale 常很高，設為 3000 避免大量請求。

## 對外 API 與輸出（`streamdl/api.py`）

- `download()` / `adownload()`：建立 `Options`（`extra="forbid"`）→ `Pipeline.run()` → `DownloadResult`（`core/result.py`）。
- 輸出：`Message.push()` 依序使用 `CURRENT_PUSHER`（contextvar，API 為每次呼叫設定）→ 全域註冊（CLI 的 `RichPusher`）→ `LoggingPusher`（logger `streamdl`，掛 `NullHandler`）。import 時不註冊任何 Pusher。
- `HookPusher`：把訊息轉成 `{"type": "log" | "progress", ...}` 交給 `progress_hook`；hook 拋出的例外會被記錄並忽略。
- 互動：`log.INTERACTIVE`（contextvar）覆寫 `log.interactive()`；API 預設 False，因此不詢問帳密 / 標題、不等待 Enter。
- contextvar 會被 asyncio 建立的子任務繼承，所以同一程式中並行的多個 `adownload` 各自使用自己的 hook。
- 瀏覽器相關套件（undetected-chromedriver）為選用（`streamdl[browser]`）；只在 `ExtractContext.new_browser` 載入，缺少時提示安裝方式。

## 停止與續傳

- 全部任務結束後若仍有瀏覽器，`Pipeline._keep_browsers_open` 等待使用者按 Enter（或 Ctrl+C）才關閉（`--no-keep-browser` 停用）。`log.ask` 以 daemon 執行緒讀取輸入並可被停止訊號中斷，放棄等待時程式結束不會卡在 `input()`。

- 第一次 Ctrl+C：停止追蹤直播新片段，完成進行中下載後照常產生清單與合併。
- 第二次 Ctrl+C：強制中斷。
- 重新執行相同指令：讀取 `store.json`，已完成的片段（檔案以 `.part` 寫完才改名，存在即完整）直接略過。

## ZAN-LIVE（`extractor/adapters/zan_live/`）

| 檔案 | 內容 |
|---|---|
| `urls.py` | 網址集中管理（domain 可替換供測試），detail / playroom 網址解析（任意語系前綴） |
| `pages.py` | 純解析：meta → pydantic、參演者、封面、禮物、留言清單、CSRF、選票規則 |
| `auth.py` | httpx 表單登入、瀏覽器內登入（有帳密自動填寫，否則手動） |
| `attachments.py` | 附件清單：`images/`（logos、artists、gifts）、`raw comments/`、`web info/tickets/`、`web info/attachments/`（禮物 JSON，舊版為 `web info/gifts/`） |
| `extractor.py` | 流程：查詢票券 → 選票 → 等待開播 → 每個視角獨立登入並由瀏覽器進入直播間 → 串流 + 附件 |

- 帳密：環境變數 `STREAMDL_ACCOUNT` / `STREAMDL_PASSWORD`、`--account` / `--password`，或執行時於終端機輸入（密碼不回顯；直接 Enter 改為瀏覽器手動登入）。
- **每個視角的流程**：獨立 Session 登入 → 開啟專屬瀏覽器並帶入登入狀態 → **由瀏覽器進入該視角直播間** → 從瀏覽器頁面取得串流網址、從瀏覽器讀回 cookies → 開始下載。
  - 不同視角共用 cookies / 登入狀態會互相干擾，因此各自登入、各自一個瀏覽器（依序開啟）。
  - 進入或重新整理直播間會改變伺服器端播放狀態，下載端必須使用「最後進入直播間」的那份 session；因此直播間頁面只由瀏覽器開啟，httpx 從不讀取直播間。
  - 下載期間每 10 秒從瀏覽器同步 cookies（瀏覽器為權威，合併而非取代）。
- 下載中 401/403：先從瀏覽器同步 cookies；60 秒內再次失敗則讓瀏覽器重新進入直播間後再同步。
- 瀏覽器在整個下載結束後才關閉；ZAN-LIVE 不支援 `--browser never`。
- 輸入直播間網址時只下載該張票；輸入 detail 網址時依選票規則（直播中全部視角，否則最早開演的一組並等待）。
- 回溯關閉（`backfill=False`）。

## SINGULAR LIVE（`extractor/adapters/singular_live/`）

| 檔案 | 內容 |
|---|---|
| `urls.py` | 網址（domain / ULIZA 可替換供測試），資訊頁與直播間網址解析（任意語系） |
| `pages.py` | 純解析：`react-root` 的 `data-event`、og 標籤、區域限制訊息、選擇內容（`plan_targets`）、ULIZA params |
| `extractor.py` | 流程：資訊頁 → 瀏覽器登入確認與已購票券 → 選內容 → 等待開放 → 瀏覽器進入直播間 → ULIZA params → 串流與附件 |

- 單一瀏覽器負責整個活動（手動登入、VPN 後手動進入直播間都在同一個視窗），瀏覽器為 cookie 權威並定期同步。
- 選擇內容：存檔票直接下載；直播票 `live_detail.status == "ended"` 時改用 `related_archive.archive_content.uliza_content_id`，沒有則回報存檔尚未提供；直播票與存檔票指向同一 ULIZA 內容時只下載一次。
- 已購買判斷：`/api/mypage/available-tickets?scope=watchable` 的 `tickets[].id`；API 回應非 200 / 非 JSON 視為未登入。
- 登入：有帳密（環境變數 / 參數 / 終端機輸入）時前往 `/{lang}/login` 自動填寫 `#login-email`、`#login-password` 並點擊 `button.login-email-submit`。表單為 React 受控元件，需以 `HTMLInputElement.prototype.value` 的原生 setter 設值並觸發 `input` 事件。按鈕在 hydration 完成、欄位填寫、Cloudflare Turnstile 驗證通過前皆為 disabled：每秒檢查一次，可點擊才點；Turnstile 由瀏覽器自然完成或使用者手動勾選，程式不介入。點擊後仍停在登入頁則重試。成功判斷：頁首出現 `button.logout-button` 或已購票券 API 回應正常；失敗或沒有帳密時改為等待手動登入。
- 瀏覽器使用 `--chrome-profile` 固定設定檔（若有指定），保留登入與使用者自行安裝的擴充功能。
- 直播間網址：`/play/{tickets[n].id}/{tickets[n].contents[n].id}`。進入後若網址不是該直播間或頁面出現區域限制訊息，定期提醒並等待使用者手動進入。
- ULIZA：`player-api.p.uliza.jp/v1/players/player_05/thinkr/admin?name={uliza_content_id}` 回傳 `(function(){ var params = {...} })`；取 `src.video`（已簽章的 master playlist）、`src.poster`、`src.settings.posterSlideShow.posters`、`src.settings.seekpreview.url`。`src.settings.title` 實際格式為 `{"textJa": "..."}`。
- 此 API 不需登入即可取得簽章網址；提取器刻意只對已購買的票券讀取，未購買時不會呼叫。
- 附件布局與 ZAN-LIVE 一致（`Layout`）：`{內容}/images/`（cover、poster、seekpreview、slides/）、`{內容}/web info/tickets/uliza_params.json`、`{內容}/web info/attachments/event.json`；沒有可下載內容時放在活動資料夾本身。
- 測試：`tests/data/singular_live/` 為四種活動狀態的 data-event 樣本與去識別化的真實 ULIZA 回應。

## Twitter Space（`extractor/adapters/twitter_space.py`）

- 比對 `*.pscp.tv/…m3u8`；Session 帶 `Referer: https://x.com/`、`Origin: https://x.com`（目前伺服器不檢查）。
- 資料夾：`{播出日期} - Twitter Space #{標題}`，播出日期取自第一個片段的 `EXT-X-PROGRAM-DATE-TIME`（舊版寫死日期）。
- master 的各 variant 都是 AAC（CODECS 標示含 avc1），HLS 合併時依副檔名輸出 m4a。
- 片段 `chunk_{時間戳}_{序號}_a.aac` 有兩組變動數字，無法推出回溯模板 → `backfill=False`。
- **片段位於主播放清單路徑下**：以媒體播放清單網址解析會得到 HTTP 400。HLS 協定的替代路徑探測（`_segment_candidates`）會同時嘗試媒體與主播放清單的各層路徑（對應舊版 `get_patch_url`），此修正對所有網站生效。

## 瀏覽器監控（`extractor/adapters/browser_watch.py`）

沒有輸入網址，或網址沒有專用提取器時使用（舊版 nonspecific + AdapterDispatchCenter）：

1. 開啟瀏覽器（輸入網址則前往該頁，否則開首頁），使用者自行登入、前往播放頁並播放。
2. 瀏覽器目前網址符合網站專用提取器（如 ZAN-LIVE）時，關閉監控瀏覽器（不殘留空白視窗、釋放固定設定檔）並交給專用提取器。
3. 從 Chrome performance log 讀取 m3u8 / mpd 請求，逐一在終端機詢問是否下載（同一網址只問一次）。
4. 下載 Session 以該瀏覽器為 cookie 權威並定期同步；Referer / Origin / Authorization 沿用播放器實際送出的值（可正確處理 iframe 內的播放器）。
5. 標題：有指定 `--title` 用指定值，否則使用頁面標題。

提取器比對順序：網站專用 ZAN-LIVE / SINGULAR LIVE / Twitter Space（priority 10）→ 直接串流網址 `direct`（1000）→ 瀏覽器監控 `browser`（2000）。

## DASH（`protocol/dash/`）

| 檔案 | 內容 |
|---|---|
| `parser.py` | 純解析：BaseURL 逐層解析、SegmentTemplate（含繼承與 SegmentTimeline）、SegmentList、SegmentBase；動態 MPD 以傳入的 `now` 計算可用片段 |
| `protocol.py` | `Track`：單軌的 SegmentStore、下載、回溯、串接；`DashProtocol`：選軌、直播監控、合併 |

- 選軌：影像依 `--quality`（頻寬由高到低），音訊取最高頻寬；字幕略過。
- 加密（ContentProtection）：**在下載前**先確認金鑰 → `--key`（依 default_KID 對應）→ ClearKey 授權伺服器（同 KID 只請求一次）；都沒有則回報 DRM 系統名稱並停止，不會白下載。
- 每軌一個 `backup/{title}/{video|audio}/store.json`，排序鍵為 `$Number$` 或 `$Time$`。
- 動態 MPD 依 `minimumUpdatePeriod`（1～10 秒）重新讀取，轉為 static、連續無新片段或使用者停止時結束。
- 完成後每軌以 init + 片段串接為 fMP4（`video.mp4` / `audio.mp4`）；加密軌以 `postprocess.cenc` 解密（`*.decrypted.mp4`），再以 `postprocess.mux_tracks` 封裝。

## CENC 解密（`postprocess/cenc.py`）

- 逐 fragment 串流處理（moof + mdat），大型檔案不需整個載入記憶體。
- 原地修改、不改變任何 box 大小：`encv`/`enca` 改回 `frma` 的原始格式；`sinf`、`pssh`、`senc`、`saiz`、`saio` 改為 `free`。因此不需重算 `trun.data_offset`、`stco` 等偏移。
- `cenc`：AES-CTR，同一樣本的所有加密區段共用一條連續金鑰流（IV 補零至 16 位元組）。已以 ffmpeg 的非分段 CENC 解密結果為獨立參考驗證（100/100 樣本相同）。
- `cbcs`：AES-CBC pattern（例如 1:9），每個加密區段以相同的 constant IV 重新開始，尾端不足 16 位元組保留明文。
- 錯誤金鑰在 AES-CTR 下無法偵測 → 解密後以 ffmpeg 試解前 3 秒，失敗則警告。
- 測試資料：`tests/unit/cenc_fixture.py` 的加密器會在每個 traf 寫入 senc（ffmpeg 的 CENC 輸出缺少 fragment 層級的 senc，無法作為測試資料）。

## HLS 加密

- 同一組片段可能列出多個 `EXT-X-KEY`（不同 KEYFORMAT）：優先選可直接下載金鑰的 identity。
- `skd://`、非 identity 的 KEYFORMAT、`SAMPLE-AES-CTR` 視為 DRM，回報系統名稱（FairPlay / Widevine / PlayReady）並停止。
- `SAMPLE-AES` 只加密部分資料，無法逐段解密，由 ffmpeg 合併時解密；本地 `media.m3u8` 寫出實際的 METHOD。
- 多 Period 只取第一個（動態取最後一個）。
